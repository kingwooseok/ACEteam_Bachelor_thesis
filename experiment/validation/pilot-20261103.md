## P02 — 배경 네트워크 855 Mbps 선택

UDP 단방향·1스트림·단계당 10초로 목표 전송률을 올렸다.
iperf3가 선택한 실제 UDP 데이터그램 크기는 모든 실행에서 **1,448바이트**였다.

| 단계 | 목표 Mbps | 실제 송신 Mbps | 실제 수신 Mbps | 송수신 패킷 수 차이 |
|---|---:|---:|---:|---:|
| 상승 측정 | 400 | 399.986 | 399.975 | 0 |
| 상승 측정 | 600 | 599.983 | 599.968 | 0 |
| 상승 측정 | 800 | 799.975 | 799.952 | 0 |
| 상승 측정 | 900 | 899.971 | 899.945 | 0 |
| 기준 후보 | 950 | 949.972 | 949.945 | 0 |
| 상단 탐색 | 970 | 956.432 | 956.346 | 49 |
| 기준 재현 | 950 | 949.969 | 949.943 | 0 |
| 선택값 검증 1 | 855 | 854.975 | 854.951 | 0 |
| 선택값 검증 2 | 855 | 854.976 | 854.952 | 0 |
| 재부팅·IRQ 정렬 후 재검증 | 950 | 949.969 | 949.653 | 0 |
| 재부팅·IRQ 정렬 후 재검증 | 855 | 854.976 | 854.719 | 0 |

950 Mbps 목표를 유지한 반복 측정을 기준 `R`로 선택했다.
970 Mbps를 요청하면 실제 송신이 약 956 Mbps에 머물렀다.
따라서 세 수신 구성에 공통으로 적용할 고부하는 다음과 같다.

```text
network_high_bps = 950,000,000 × 0.9 = 855,000,000
```

950·855 Mbps 실행은 송수신 패킷 수가 같고 iperf 손실도 0이었다.
970 Mbps 실행은 iperf 손실 필드가 0이지만 송수신 수가 49개 차이 났다.
최초 9회 전후 상태에서 NIC 오류·드롭과 softnet 드롭 증가량은 모두 0,
throttle 상태는 `0x0`였다.

원본 iperf JSON 11개와 요약값은 [P02 측정 자료](pilot-20261103/p02-summary.json)에,
최초 9회 상태 변화는 [상태 점검 기록](pilot-20261103/p02-state-audit-initial.json)에 있다.

## P03 — 세 경로·CPU 배치·시각 계측

추가 부하 없이 각 구성에서 세 흐름을 10초씩 실행했다.
흐름마다 목표 10,000개, 종료 대기 500 ms, drain 100 ms를 사용했다.

| 구성 | 일반 9000 | 중요1 9001 | 중요2 9002 | 송신 → 수신 | 구간 합 일치 |
|---|---|---|---|---:|---:|
| all-pass | PASS | PASS | PASS | 30,000 → 30,000 | 30,000 |
| pass-xsk | PASS | PASS | AF_XDP | 30,000 → 30,000 | 30,000 |
| mixed | PASS | CPUMAP | AF_XDP | 30,000 → 30,000 | 30,000 |
| **합계** | | | | **90,000 → 90,000** | **90,000** |

- 수신 앱의 허용 CPU와 OTHER/0 정책이 모든 구성에서 설정과 일치했다.
- mixed의 중요1은 CPU 3, 일반·AF_XDP 앱은 CPU 0–2를 사용했다.
  전용 partition 생성과 종료 후 CPU 0–3 반환이 모두 `verified=true`로 기록됐다.
- CPUMAP 커널 스레드는 CPU 3·OTHER/0으로 기록됐다.
- PHC 보정범위 밖 표본, 구간 분해의 무효·불일치 표본은 모두 0이었다.
  `L_total = d₁+d₂+d₃`의 최대 절대 잔차는 0 ns였다.
- AF_XDP의 기록 overflow·메타데이터 오류·UMEM 불변식 오류는 모두 0이었다.

첫 P03에서 하드웨어 IRQ 증가량은 CPU 2에만 기록됐지만, IRQ 스레드의 허용 CPU는
all-pass·pass-xsk에서 `0–3`, mixed에서 `0–2`였다.
같은 IRQ 요청값 `2`를 다시 쓰자 스레드 허용 CPU도 `2`로 갱신됐다.
이에 실행 준비에서 IRQ 요청을 매번 재적용하고 실제 IRQ 스레드까지 검사하도록 수정했다.

첫 P03의 [실행·계측 요약](pilot-20261103/p03-initial-summary.json),
[조건 파일](pilot-20261103/configs/p03-paths.conf),
[IRQ 재적용 기록](pilot-20261103/irq-reapplied.txt)을 함께 보존했다.

## 예비시험 중 수정한 실행·분석 동작

| 발견한 동작 | 반영한 수정 | 검증 대상 |
|---|---|---|
| Windows 분석 출력에서 `O_CLOEXEC` 오류 | 플랫폼에 맞는 파일 열기와 줄바꿈·완료 기록 처리 | 실제 P03 자료의 Windows 분석, 분석 테스트 |
| IRQ 요청값이 이미 2면 재적용 생략 | 같은 값도 재적용하고 IRQ 스레드 affinity까지 검사 | 오래된 스레드 배치의 갱신과 실패 검출 |
| 배경 송신 중 XDP 로더 종료로 NIC 링크 재시작 | 송신 부하 종료 ACK → 수신 부하 종료 → XDP 해제 순서 | ACK 대기 중 서버·로더 유지, 종료 순서 |
| 전체 관측 시간으로 NIC 평균을 계산 | NIC 카운터와 MONOTONIC 시각을 기록하고 실제 수신 측정창으로 집계 | 측정창 경계 가중·표본 범위 검사, 60초 리허설 |

첫 P04의 `p04-r1-s0-all-pass-r0001`은 수신 기록 30,000개를 저장한 뒤
송신 측 ACK 대기에서 시간 초과가 발생했다. 송신 Pi의 두 연결이 응답하지 않아
재부팅했고, 해당 실행은 실패 기록으로 보존했다.
수신 로그에서 XDP 해제 시 NIC 링크가 재시작되는 동작을 확인해 위 종료 순서를 반영했다.

## P04 — 종료 대기 0 ms 선택

각 흐름 1,000 PPS, CPU 워커 3개·855 Mbps 배경 트래픽, drain 100 ms를 유지했다.
종료 대기값마다 세 수신 구성을 각각 3회씩 실행했다. 한 실행의 송신 시간은 10초이며,
대기값과 구성의 실행 순서를 반복별로 순환했다.

| 추가 종료 대기 | 실행 수 | 송신 → 수신 | 누락 시퀀스 | AF_XDP drain 추가 수신 |
|---|---:|---:|---:|---:|
| **0 ms** | 9 | 270,000 → 270,000 | 0 | 0 |
| 100 ms | 9 | 270,000 → 270,000 | 0 | 0 |
| 500 ms | 9 | 270,000 → 270,000 | 0 | 0 |
| **합계** | **27** | **810,000 → 810,000** | **0** | **0** |

모든 흐름에서 시퀀스 **0부터 9,999까지** 빠짐없이 도착했다.
송신 오류·소켓 드롭·기록 overflow·메타데이터 오류는 0이었으며,
PHC 보정과 구간 합 검사도 통과했다. 더 긴 대기로 추가 회수한 패킷이 없어
**`settle_ms=0`, `drain_ms=100`**을 선택했다.

[선택값과 집계](pilot-20261103/p04-decision.json),
[실행별 시퀀스·시각 검사](pilot-20261103/p04-tail-audit.json),
[실행 조건 파일](pilot-20261103/configs)을 함께 보존했다.

## 60초 리허설 — 본실험 길이 검증

확정한 **855 Mbps · settle 0 ms · drain 100 ms**와 CPU 워커 3개를 적용해
세 구성을 각각 60초씩 실행했다. 각 흐름은 60,000개를 송신했다.

| 구성 | 송신 → 수신 | 누락 시퀀스 | NIC 수신 Mbps | CPU·NIC 측정창 포함률 |
|---|---:|---:|---:|---:|
| all-pass | 180,000 → 180,000 | 0 | 881.363 | 100% |
| pass-xsk | 180,000 → 180,000 | 0 | 881.010 | 100% |
| mixed | 180,000 → 180,000 | 0 | 879.574 | 100% |
| **합계** | **540,000 → 540,000** | **0** | | **100%** |

모든 흐름의 시퀀스 0–59,999가 중복·누락 없이 기록됐다. PHC 보정범위 밖 표본과
구간 합 불일치는 0이었고 최대 잔차는 0 ns였다. 송신 오류·수신 소켓 드롭·기록 overflow·
메타데이터 오류·UMEM 불변식 오류와 NIC 오류·드롭도 모두 0이었다.

CPU와 NIC는 **최초 XDP 관측부터 마지막 사용자 수신까지 같은 MONOTONIC 측정창**으로
집계했다. 두 지표 모두 측정창 전체가 표본으로 덮였고, 양 끝의 표본 구간은 겹친 시간만
반영했다. 위 NIC Mbps는 계측 패킷·배경 트래픽과 NIC가 세는 헤더 바이트를 포함한다.
855 Mbps는 iperf3 UDP 부하의 설정값이다.

[패킷 순번·시각 검사](pilot-20261103/rehearsal-tail-audit.json)를 보존했다.
