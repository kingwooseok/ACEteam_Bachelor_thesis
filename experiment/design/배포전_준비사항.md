# 공유 일반 영역과 중요 수신 분리를 위한 실험 준비

## 이번 실험이 비교하는 것

일반 Linux 소켓으로 모두 받는 구성에서 시작해, AF_XDP 직접 수신을 추가하고,
중요 흐름만 CPUMAP으로 전용 CPU에 분리한다. CPU·네트워크 부하가 증가할 때
세 구성의 지연·손실·처리량과 구간별 시간 변화를 비교한다.

| 구성 | 일반 9000 | 중요1 9001 | 중요2 9002 | 수신 실행 영역 |
|---|---|---|---|---|
| all-pass | PASS | PASS | PASS | 모두 CPU 0·1·2 공유 |
| pass-xsk | PASS | PASS | AF_XDP | 모두 CPU 0·1·2 공유 |
| mixed | PASS | CPUMAP | AF_XDP | 중요1의 커널 처리·수신만 CPU 3 |

공유 영역은 세 구성에서 같은 CPU 0·1·2이며 CPU 3은 중요 수신용으로 예약한다.
PASS와 AF_XDP 앱은 이 공유 집합 안에서 Linux가 스케줄링한다.
CPUMAP의 CPU 전달 비용을 포함한 총지연을 평가하고, 네 관측점으로 변화가 나타난
구간을 설명한다.

## 실행표: 13조건 · 165회

| 묶음 | 조건 | 실행 수 |
|---|---|---:|
| 단독 | mixed에서 활성 흐름 하나씩, 3경로 × 5회 | 15 |
| A·B | 중복 제외 10조건 × 세 구성 × 5회 | 150 |
| 합계 | 단독 15회 + 본실험 150회 | **165** |

- A: CPU 부하 0%/100% × 배경 네트워크 0/고부하의 네 조건.
- B: 일반 0/1,000/3,000/최고 PPS × CPU 부하 0%/100%의 여덟 조건. 배경 네트워크 부하 0.
- A·B 중복 두 조건은 같은 결과를 함께 사용한다.
- 공유 CPU 부하 위치는 0·1·2로 유지한다. C의 워커·수신 앱 이동 조건은 삭제했다.

각 run은 60초 송신, 부하 안정화 5초다. 중요 흐름은 각 1,000 PPS,
비교 기한은 NIC 수신부터 100µs이며 각 구성·조건을 5회 반복한다.

## CPU와 스케줄링 배치

| 역할 | 송신 Pi | 수신 Pi |
|---|---|---|
| 일반 9000 | CPU 0, OTHER/0 | CPU 0·1·2 공유, OTHER/0 |
| 중요1 9001 | CPU 1, FIFO/80 | all-pass·pass-xsk는 0·1·2 공유 / mixed는 3, OTHER/0 |
| 중요2 9002 | CPU 2, FIFO/80 | CPU 0·1·2 공유, OTHER/0 |
| 배경 네트워크 | CPU 3, OTHER/0 | CPU 0·1·2 공유, OTHER/0 |
| 관리·관측 | CPU 3, OTHER/0 | CPU 0·1·2 공유, OTHER/0 |
| NIC IRQ | 기존 설정 | CPU 2 — 일반 공유 영역에 포함 |
| CPU 부하 | 없음 | CPU 0·1·2에 워커 하나씩, OTHER/0 |

수신 Pi의 일반 작업도 CPU 0·1·2에서 실행하도록 장치 환경을 준비한다.
CPU 3에는 mixed의 CPUMAP 전달 워커와 중요1 수신 앱을 배치한다.
수신 Pi의 기존 부팅 명령줄에 아래 두 인자를 적용한 뒤 재부팅한다.
기존 `isolcpus`·`irqaffinity` 항목이 있으면 같은 항목을 중복 추가하지 않고 값을 맞춘다.

```text
isolcpus=domain,3 irqaffinity=0-2
```

CPU 3의 일반 스케줄링 영역 제외와 기본 IRQ 배치를 준비한 뒤 다음으로 검사한다.

```bash
bash monitor/check_cpu_partition.sh eth0 0,1,2 3
```

검사는 CPU 3 예약과 공유 영역 분리, RPS 비활성·기본 NAPI 실행 상태를 읽는다.
실제 수신 실행도 같은 검사를 수행하고 부적합하면 시작 전에 중단한다.
실행기는 부팅 설정을 수정하거나 장치를 재부팅하지 않는다.
세 비교 구성에서 같은 예약 상태를 유지하며 CPU 3은 mixed의 중요 수신에 사용한다.

profile은 `receiver_shared_cpus=[0,1,2]`, `receiver_cpumap_cpu=3`을 사용한다.
생성된 설정의 `receiver.shared_cpus=0,1,2`가 일반 자식들의 공통 허용 집합이다.
`flowN.rx_cpu`, `receiver.supervisor_cpu`, `receiver.network_cpu`는 `inherit`로 두고,
실행기가 mixed의 CPUMAP 수신 앱에만 CPU 3을 적용한다.

`run.json`의 `rx_cpus`에는 `"0,1,2"` 또는 `"3"`을 기록한다.
`*-flowN.placement.json`은 실제 affinity·정책·우선순위와 설정의 일치 여부를 담고,
`scheduler-ready.json`에는 IRQ·CPUMAP 스레드 상태를 남긴다.

## 예비시험에서 정할 값

1. **배치·전달 동작:** 공유 앱의 허용 CPU가 0·1·2이고 mixed의 중요1만 3인지 점검한다.
   세 경로의 패킷 수신, IRQ·CPUMAP 기록, 수신 OTHER/0 정책을 확인한다.
2. **배경 전송률:** 단방향 UDP 1스트림을 단계당 10초 측정해 기준 R을 정하고
   `network_high_bps=0.9R`를 입력한다.
3. **일반 최고 PPS:** 중요 흐름 각 1,000 PPS를 유지하고 일반 0/1,000/3,000/9,000 PPS
   후보를 시험한다. 실제 송수신·지연·손실을 보고 `pass_high_pps`를 정한다.
   선택한 최고값이 기본 후보 9,000을 대체하며 세 구성에 동일하게 적용된다.
4. **종료 대기:** 높은 부하에서 수신 수와 꼬리 표본이 안정되는 `settle_ms`를 정한다.
   `drain_ms=100`과 100µs 기한은 유지한다.

profile의 null 값은 `network_high_bps`, `pass_high_pps`, `settle_ms`다.
`receiver_address`는 수신 Pi의 시험용 Ethernet IP로 작성한다.

## 생성 → 검증 → 실행

```bash
# 초안만 생성
python3 experiment/design/build_plan.py --output /tmp/ace-plan-draft

# profile.example.json을 복사해 예비측정 값을 채운 후 새 폴더에 생성
python3 experiment/design/build_plan.py --profile /path/profile.json --output /tmp/ace-plan-final

# 장치 설정을 바꾸지 않는 native 조건 검증
./experiment/ace-run plan --config /tmp/ace-plan-final/main-01.conf

# 같은 계획 폴더를 두 Pi로 복사한 뒤 각각 실행
sudo ./experiment/run_matrix.sh receiver --plan-dir /tmp/ace-plan-final
sudo ./experiment/run_matrix.sh sender --plan-dir /tmp/ace-plan-final
```

마지막 두 명령은 각각 수신·송신 Pi에서 실행한다. 실행표 개정은
`shared-three-path-165-v2`이며 `--d01-d11`은 같은 설계를 생성하는 호환 옵션이다.
새 profile로 계획을 다시 생성한다. 실행기는 조건 파일의 해시·구성·반복 수를
검사하고 세 구성의 시작 순서를 순환한다.

## 본측정 전 60초 리허설

- 실제 송신 PPS·송수신 수·손실·유효 지연 표본 수를 집계한다.
- `ingress_update_error`, `cpumap_update_error`, `overflow_packets`를 검사한다.
- 동일 패킷의 총지연 = d₁+d₂+d₃ 및 보정 시각을 확인한다.
- 실제 수신 측정 구간의 CPU 평균과 수신 앱·커널 스레드 배치 기록을 남긴다.

기본 최고 후보의 목표 기록은 (9,000+1,000+1,000)×60=660,000개다.
생성기와 native parser는 1,048,576개 기록 한도를 함께 검사한다.
