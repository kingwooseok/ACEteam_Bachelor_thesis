# D01~D11 배포 전 준비

이 디렉터리는 실행표와 설정 파일을 준비한다. 생성기는 SSH·배포·빌드·실험 실행·장치 설정 변경을 하지 않는다. 기존 README는 수정하지 않았다.

## 준비한 내용

- D01 경로별 단독 3행을 먼저 배치했다. 단독 단계는 mixed에서 활성 흐름 하나만 1,000PPS로 실행하는 기본안이다. 각 경로를 all-PASS와 별도 비교하려면 단독 단계의 modes를 추가해 실행 수를 다시 계산한다.
- A/B/C의 동일 행을 합쳐 본시험 15행으로 정리했다. matrix.csv의 references에서 재사용 대상을 확인할 수 있다. 단독 3행×5회=15run과 본시험 15행×2모드×5회=150run을 구분한다.
- 60초, 부하 준비 대기 5초, 중요 흐름 각 1,000PPS, 중요 흐름 deadline 100,000ns, 반복 5회, 메모리/I/O/ON-OFF 부하 제외를 반영한다.
- PASS 0은 flow1.enabled=0으로 표현한다. 초당 3,000/9,000개는 정수 ns 주기의 반올림 오차가 있으므로 실제 송신 수/PPS를 분석한다.
- 미확정 profile로는 실행 가능한 .conf를 생성하지 않는다. draft/는 실행표 초안만이며 PASS 최고 9,000PPS는 예비시험 확정 전 후보값이다.

## 역할별 CPU 설정

한 설정 파일에 양쪽 역할의 값을 함께 담는다. 양쪽 Pi는 같은 파일을 사용하고 실행 역할에 해당하는 값을 선택한다.

- receiver.supervisor_cpu: 수신 관리·관측 프로세스의 CPU
- sender.supervisor_cpu: 송신 관리 프로세스의 CPU
- receiver.network_cpu: 수신 iperf3 서버 CPU
- sender.network_cpu: 송신 iperf3 클라이언트 CPU (D06 목표 CPU3)
- flowN.tx_cpu / rx_cpu: 흐름별 송신기 / 수신기 CPU

역할별 supervisor가 생략되면 기존 supervisor_cpu로 되돌아가므로 과거 설정과 호환된다. network_cpu=inherit이면 해당 역할 관리 프로세스 affinity를 상속한다. 수신 부하 worker는 이 값과 별도로 load.cpu_cpus를 사용한다. CPU 선택은 실행 중 실제 affinity로도 확인해야 한다.

## 모드 실행 순서

alternate_mode_order=1이면 반복마다 시작 모드를 뒤집는다. modes=all-pass,mixed의 5회는 AB / BA / AB / BA / AB다. 생성기는 다음 조건에서 기본 순서를 뒤집어 전체적으로 시작 순서를 분산한다. 5회이므로 각 조건 안에서 선행 횟수는 3:2이며 완전 균형은 아니다. 무작위 실행은 아니고, 같은 설정에서 재현 가능한 순서다. 기존 설정은 기본값 0으로 기존 순서를 유지한다.

## 아직 확정해야 할 입력

profile.example.json의 null은 다음 선택이 필요함을 뜻한다. 테스트 코드의 숫자를 본시험 결정값으로 사용하지 않는다.

1. 기본 PASS/AF_XDP 수신 CPU, 흐름별 송수신 정책과 우선순위. CPUMAP 수신 CPU3은 고정한다.
2. 역할별 관리 CPU와 수신 iperf CPU. 수신 관리/iperf는 CPU0~2에서 선택한다.
3. 네트워크 high/middle bps 및 PASS 최고 PPS. 예비 측정으로 확정해야 하며 후보를 검증된 포화값으로 표현하지 않는다.
4. settle_ms: 송신 완료 후 늦은 패킷을 수신할 시간. drain_ms=100의 후속 종료 단계와 구분한다.

## 생성 및 배포 전 확인

저장소 최상위에서 실행한다. 출력은 새 디렉터리여야 하며 기존 결과를 덮어쓰지 않는다.

```bash
# 미확정 값이 있는 실행표만 생성(.conf 없음)
python3 experiment/design/build_plan.py --output /tmp/ace-plan-draft

# profile.example.json을 별도 파일로 복사해 null을 채운 후 실행
python3 experiment/design/build_plan.py --profile /path/to/profile.json --output /tmp/ace-plan-final

# Linux에서 빌드된 제어기로 각 설정을 검증. plan은 장치를 변경하지 않는다.
./experiment/ace-run plan --config /tmp/ace-plan-final/main-01.conf
```

profile을 채워 .conf가 생성돼도 상태는 configured-unvalidated다. 실제 실행 검증 완료를 뜻하지 않는다. 단독→본시험 순서는 matrix.csv를 사용하며 파일명 glob의 정렬 순서에 의존하지 않는다. 전체 행을 자동 실행하는 배포/SSH 도구는 추가하지 않았다.

## 설계 해석

CPU 부하를 0,1,2에서 0,1,2,3으로 늘리면 총 worker 수가 증가한다. 이를 동일 총부하에서 위치만 바꾼 시험이라고 주장하지 않는다. PASS 증가 시험은 총 PPS와 비율이 함께 변한다. 100µs는 이번 연구가 선택한 비교 기준이고, 5초 대기는 실제 정상상태 보증이 아니다. 반복 신뢰구간은 run 통계의 불확실성을 나타내며 hard deadline 보장이 아니다.

## 2026-10-29 배포 전 검증 결과

- 로컬 설계/환경 회귀 검사: 15개 중 14개 통과, Linux 전용 1개 skip.
- 수신 Pi의 기존 임시 RAM 복사본에서 tests/run_offline.sh 전체 통과: Python suite 42개 + 41개 + 7개, 총 90개 통과 및 빌드/스크립트 검사 통과.
- 생성한 18개 행 설정을 네이티브 plan 파서가 모두 수락하는 것을 확인했다. 본시험 수치로 사용하지 않는 회귀 검사용 profile을 사용했다.
- loopback 실제 iperf3 서버/클라이언트의 역할별 CPU affinity와 두 ace-run 관리 프로세스의 개별 CPU affinity를 검사했다.
- 실제 실험 폴더에 배포하거나 본시험을 실행하지 않았다. root 권한, IRQ/governor/서비스 변경 없이 실행했다. 본시험의 미확정 profile은 그대로 남겼다.
