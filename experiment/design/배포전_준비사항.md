# 공유 일반 영역과 중요 수신 분리를 위한 실험 준비

## 이번 실험이 비교하는 것

일반 Linux 소켓으로 모두 받는 구성에서 시작해, AF_XDP 직접 수신을 추가하고,
중요 흐름만 CPUMAP으로 전용 CPU에 분리한다. CPU·네트워크 부하가 증가할 때
세 구성의 지연·손실·처리량과 구간별 시간 변화를 비교한다.

| 구성 | 일반 9000 | 중요1 9001 | 중요2 9002 | 수신 실행 영역 |
|---|---|---|---|---|
| all-pass | PASS | PASS | PASS | 모두 CPU 0·1·2·3 공유 |
| pass-xsk | PASS | PASS | AF_XDP | 모두 CPU 0·1·2·3 공유 |
| mixed | PASS | CPUMAP | AF_XDP | 중요1은 CPU 3, 나머지는 CPU 0·1·2 공유 |

세 구성 모두 총 네 개의 CPU를 사용한다. all-pass·pass-xsk는 네 개를 함께 쓰고,
mixed는 CPU 3을 중요1 전용으로 분리한다. PASS·AF_XDP 앱과 일반 Linux 프로그램은
각 구성의 일반 실행 영역 안에서 Linux가 스케줄링한다.
CPUMAP의 CPU 전달 비용을 포함한 총지연을 평가하고, 네 관측점으로 변화가 나타난
구간을 설명한다.

## 고정 입력과 네 부하 조건

일반 9000·중요1 9001·중요2 9002는 각각 **1,000 PPS**로 고정한다.
같은 입력에서 CPU 연산 부하와 iperf3 배경 네트워크 부하를 조절한다.

| 본실험 조건 | CPU 연산 부하 | iperf3 배경 네트워크 부하 |
|---|---|---|
| 기본 상태 | 끔 | 끔 |
| CPU 경합 | 켬 | 끔 |
| 네트워크 부하 | 끔 | 고부하 |
| 복합 부하 | 켬 | 고부하 |

iperf3의 UDP/5201 패킷은 PASS로 일반 커널 스택에서 처리한다.
실제 일반 통신량은 9000번 계측 흐름과 iperf3 배경 트래픽을 합한 양이다.
세 구성에 같은 배경 전송률을 적용하고 실제 송수신량과 손실을 기록한다.

## 실행표: 7조건 파일 · 75회

| 묶음 | 조건 | 실행 수 |
|---|---|---:|
| 단독 | PASS/all-pass, CPUMAP/mixed, AF_XDP/pass-xsk에서 한 흐름씩 × 5회 | 15 |
| 부하 본실험 | 4조건 × 세 구성 × 5회 | 60 |
| 합계 | 단독 15회 + 본실험 60회 | **75** |

세 구성에서 부하 워커 세 개의 수와 강도를 유지하고, 구성별 일반 영역 전체를 공유한다.
CPU 부하 끔에서는 워커를 실행하지 않고, 켬에서는 세 워커를 각각 100% 강도로 실행한다.

각 run은 60초 송신, 부하 안정화 5초다. 세 계측 흐름은 각 1,000 PPS,
비교 기한은 NIC 수신부터 100µs이며 각 구성·조건을 5회 반복한다.

## CPU와 스케줄링 배치

| 역할 | 송신 Pi | 수신 Pi |
|---|---|---|
| 일반 9000 | CPU 0, OTHER/0 | 구성별 일반 영역 공유, OTHER/0 |
| 중요1 9001 | CPU 1, FIFO/80 | all-pass·pass-xsk는 0·1·2·3 공유 / mixed는 3, OTHER/0 |
| 중요2 9002 | CPU 2, FIFO/80 | 구성별 일반 영역 공유, OTHER/0 |
| 배경 네트워크 | CPU 3, OTHER/0 | 구성별 일반 영역 공유, OTHER/0 |
| 관리·관측 | CPU 3, OTHER/0 | 구성별 일반 영역 공유, OTHER/0 |
| NIC IRQ | 기존 설정 | CPU 2 — 일반 공유 영역에 포함 |
| CPU 부하 | 없음 | 세 워커가 구성별 일반 영역 공유, OTHER/0 |

**구성별 일반 영역:** all-pass·pass-xsk는 CPU 0·1·2·3, 활성 CPUMAP 중요1이 있는
mixed는 CPU 0·1·2다. CPU 부하 세 워커는 이 허용 집합을 함께 사용한다.
`load.cpu_percent=100`은 각 워커의 목표 강도이며 CPU별 실제 사용률을 함께 기록한다.

수신 Pi는 네 CPU가 일반 스케줄링에 참여하는 부팅 상태로 준비한다.
이전에 `isolcpus=domain,3`을 적용했다면 해당 고정 격리를 제거하고 재부팅한다.
실행기는 cgroup v2의 CPU partition으로 다음 전환을 수행한다.

1. **all-pass·pass-xsk:** 일반 Linux 작업과 모든 수신 앱이 CPU 0~3을 공유한다.
2. **mixed 준비:** 중요1이 활성화되어 있으면 CPU 3 전용 영역을 만든다. 일반 작업은
   CPU 0~2를 사용하고 CPUMAP 커널 처리와 중요1 수신 앱은 CPU 3에서 실행한다.
3. **종료·실패 정리:** 수신기·로더와 부하를 종료한 뒤 전용 영역을 해제한다.
   CPU 0~3의 일반 공유를 복원하고 다음 구성으로 넘어간다.

단독 PASS는 all-pass, 단독 AF_XDP는 pass-xsk로 실행해 네 CPU를 공유한다.
CPUMAP 단독만 mixed의 중요1을 켜서 CPU 3을 예약한다.
실행 전 상태는 다음 명령으로 검사한다.

```bash
bash monitor/check_cpu_partition.sh eth0 0,1,2,3 3
```

검사는 네 CPU의 사용 가능 상태, 고정 부팅 격리, cgroup v2 CPU 관리 기능과
RPS 비활성·기본 NAPI 상태를 읽는다. 실제 수신 실행도 같은 검사를 수행한다.
NIC IRQ는 모든 구성에서 CPU 2를 사용하며 실행기가 준비 단계에서 적용한다.
CPU 영역 전환은 측정 전후에 수행하고, 측정 중에는 준비한 배치를 유지한다.

profile은 `receiver_shared_cpus=[0,1,2,3]`, `receiver_cpumap_cpu=3`을 사용한다.
생성된 설정의 `receiver.shared_cpus=0,1,2,3`이 전체 사용 가능 CPU 집합이다.
`flowN.rx_cpu`, `receiver.supervisor_cpu`, `receiver.network_cpu`는 `inherit`로 두고,
실행기가 구성별 허용 집합을 적용한다. CPU 부하는 `load.cpu_layout=shared`,
`load.cpu_workers=3`, `load.cpu_cpus=0,1,2,3`에서 구성별 일반 영역을 사용한다.

`run.json`의 `rx_cpus`에는 `"0,1,2,3"`, `"0,1,2"` 또는 `"3"`을 기록한다.
`*-flowN.placement.json`은 실제 affinity·정책·우선순위와 설정의 일치 여부를 담고,
`scheduler-ready.json`에는 IRQ·CPUMAP 스레드 상태를 남긴다.
CPU 3을 예약한 실행에는 `cpu-partition-active.json`과 `cpu-partition-restored.json`으로
실제 분리 상태와 반환 결과를 남긴다.

## 본실험을 위한 세 가지 준비

1. **배치·전달 동작:** all-pass·pass-xsk의 CPU 0~3 공유, mixed의 CPU 0~2 일반 영역과
   중요1 CPU 3 분리, 실행 후 CPU 0~3 복원을 점검한다. 세 경로의 패킷 수신,
   IRQ·CPUMAP 기록, 수신 OTHER/0 정책을 확인한다.
2. **배경 전송률:** 단방향 UDP 1스트림을 단계당 10초 측정해 기준 R을 정하고
   `network_high_bps=0.9R`를 입력한다.
3. **종료 대기:** 높은 부하에서 수신 수와 꼬리 표본이 안정되는 `settle_ms`를 정한다.
   `drain_ms=100`과 100µs 기한은 유지한다.

profile의 null 값은 `network_high_bps`, `settle_ms`다.
`receiver_address`는 수신 Pi의 시험용 Ethernet IP로 작성한다.

## 생성 → 검증 → 실행

```bash
# 초안만 생성
python3 experiment/design/build_plan.py --output /tmp/ace-plan-draft

# profile.example.json을 복사해 예비측정 값을 채운 후 새 폴더에 생성
python3 experiment/design/build_plan.py --profile /path/profile.json --output /tmp/ace-plan-final

# 장치 설정을 바꾸지 않는 native 조건 검증
./experiment/ace-run plan --config /tmp/ace-plan-final/main-01.conf

# 같은 계획 폴더를 두 Pi로 복사한 뒤 각각 실행
sudo ./experiment/run_matrix.sh receiver --plan-dir /tmp/ace-plan-final
sudo ./experiment/run_matrix.sh sender --plan-dir /tmp/ace-plan-final
```

마지막 두 명령은 각각 수신·송신 Pi에서 실행한다. 실행표 개정은
`fixed-1000pps-75-v4`이며 `--d01-d11`은 같은 설계를 생성하는 호환 옵션이다.
새 profile로 계획을 다시 생성한다. 실행기는 조건 파일의 해시·구성·반복 수를
검사하고 세 구성의 시작 순서를 순환한다.

## 본측정 전 60초 리허설

- 실제 송신 PPS·송수신 수·손실·유효 지연 표본 수를 집계한다.
- `ingress_update_error`, `cpumap_update_error`, `overflow_packets`를 검사한다.
- 동일 패킷의 총지연 = d₁+d₂+d₃ 및 보정 시각을 확인한다.
- 실제 수신 측정 구간의 CPU 평균과 수신 앱·커널 스레드 배치 기록을 남긴다.

본실험의 목표 계측 기록은 (1,000+1,000+1,000)×60=180,000개다.
단독 측정은 해당 흐름 하나의 60,000개를 기록한다.
생성기와 native parser는 1,048,576개 기록 한도를 함께 검사한다.
